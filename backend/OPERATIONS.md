# 백업·복원·초기화 운영 점검

이 문서는 운영자가 수행할 절차입니다. 작성 과정에서 운영 계정이나 DB에 접속하지 않았으며 백업 생성·복원·초기화를 실행하지 않았습니다.

## 백업 확인

1. Render에서 대상 서비스와 `scutta-db`의 연결 관계, PostgreSQL 버전, 실제 요금제를 확인합니다. 유료 Render Postgres의 PITR 복구 가능 기간은 workspace 요금제에 따라 달라지므로 DB의 **Recovery** 화면에서 현재 복구 가능한 시점을 확인합니다.
2. 초기화나 대규모 삭제 전, 사용자의 기록 입력이 중단된 시간을 확보하고 논리 백업 export를 생성합니다. 완료 시각과 다운로드 가능 여부를 확인하고 접근을 제한한 별도 저장소에 보관합니다. 백업에는 계정·세션 정보가 포함되므로 Git, 채팅, 공개 파일 공유에 올리지 않습니다.
3. DB 이름, 백업 시각과 시간대, 앱 커밋, Alembic revision, 주요 테이블 건수만 운영 기록에 남깁니다. 비밀번호와 연결 문자열은 기록하지 않습니다. 허용 데이터 손실 시간(RPO)과 복구 시간(RTO)은 운영자가 정합니다.

Render는 PITR로 별도 DB를 생성하며 논리 백업도 내보낼 수 있습니다. 실제 보존 기간과 복구 제한은 실행 전에 [Render 공식 복구 안내](https://render.com/docs/postgresql-backups)를 다시 확인합니다.

## 분리된 DB에서 복원 검증

1. PITR은 구분되는 새 DB 이름으로 복구합니다. 논리 백업은 운영과 다른 **빈 DB**에 복원합니다. 원본 운영 DB나 운영 `DATABASE_URL`을 덮어쓰지 않습니다. PostgreSQL 주 버전에 맞는 복원 도구를 사용하고 대상 호스트·DB 이름을 실행 전에 다시 대조합니다.
2. 복원 DB의 접근을 제한합니다. 복원된 Alembic revision에 맞는 앱 버전으로 확인하며, 최신 앱의 시작 명령을 무심코 실행해 먼저 마이그레이션하지 않습니다. 선수·경기·대회·대진·팀·미니게임 건수와 대표 결과, 랭킹·정산, 대진과 경기의 연결을 점검합니다.
3. 운영 전환이 필요하면 입력을 중단하고 복원 시점 이후 기록의 처리 방식을 결정합니다. 검증된 DB로 서비스 연결을 변경한 뒤 로그인·조회·경기 제출을 확인합니다. 기존 DB는 확인이 끝날 때까지 보존하고, 이후 보존·폐기 일정을 기록합니다. 복원 소요시간과 결과를 기록해야 복구 훈련 완료로 간주합니다.

## 학기 초기화 직전과 직후

1. 대상 환경·DB·삭제 범위를 확인합니다. 앱의 초기화 미리보기 건수를 운영 기록과 비교합니다. 경기·대회·선수·선수 세션·미니게임 기록은 삭제되고 관리자와 정산 상품 설정은 유지됩니다.
2. 백업 완료 및 분리 DB 복원 검증, 복구 담당자와 복구 경로를 확인합니다. 다른 관리자의 작업과 선수 입력이 계속되는 동안에는 초기화하지 않습니다. 관리자 비밀번호와 화면의 확인 문구는 실제 초기화 화면에만 입력합니다.
3. 완료 후 경기·대회·선수 기록 제거와 관리자 로그인·상품 설정 보존을 확인합니다. 실패나 예상과 다른 건수가 나오면 반복 초기화하지 말고 서버 로그와 DB 상태를 먼저 확인합니다. 복구는 위의 분리 DB 절차로 진행합니다.
