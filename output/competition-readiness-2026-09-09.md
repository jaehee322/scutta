### 운영 조건: 단체 입력에는 PostgreSQL 사용

로컬 개발용 SQLite에서는 행 잠금이 적용되지 않아 다음 경합을 재현했다.

- 같은 복식에 양 팀이 상반된 점수를 동시에 제출하면 두 요청이 성공하고 마지막 점수로 덮어써진다.
- 첫 결과 입력과 참가자 편성 변경이 겹치면 화면의 대진 선수와 개인 통계의 선수가 달라질 수 있다.

운영 구성인 PostgreSQL에서는 두 번째 요청이 대회 행 잠금을 기다리는 것을 직접 관찰했다. 첫 결과가 우선이면 후속 중복 제출·편성 변경이 거절됐고, 편성이 먼저 바뀌면 오래된 대진의 결과 입력이 거절됐다. 최초 점수 및 선수 연결은 보존됐다. **이번 행사 기록은 운영 PostgreSQL 서버에서 진행하고, 로컬 SQLite 서버를 여러 사람의 실제 기록 입력용으로 사용하지 않는 것이 맞다.** [잠금 구현](C:/Users/jaehe/scutta/backend/app/services/competitions.py:131).

### 선택 개선: 팀이 많은 단체전에서 대결 찾기

현재 단체전은 모든 대결을 펼쳐 표시한다. 20팀을 가정하면 190대결이며, 전부 2:2 복식까지 마친 가상 데이터에서는 DOM 약 2만 개, 페이지 높이 약 10.5만 px였다. 오류는 없었지만 원하는 대결을 찾는 데 많은 스크롤이 필요하다.

실제 팀이 많다면 **내 팀 필터 또는 팀 선택 필터**가 가장 실용적인 후속 개선이다. 현재 점검에서는 화면 구조를 크게 바꾸지 않았다. 이 수치는 로컬 데스크톱 브라우저의 가상 데이터 결과이며 저사양 모바일의 속도 보장이 아니다.

## 운영 환경과 검증의 한계

저장소의 `render.yaml`은 무료 Web Service와 유료 PostgreSQL 구성을 선언한다. 실제 서비스 설정이 이와 같은지는 별도 확인이 필요하다. 무료 Web Service는 요청이 15분 없으면 중지되고 재기동에 약 1분이 걸릴 수 있다. 행사 시작 직전에 운영 앱에 로그인하고 대회 목록이 열리는지 확인해 첫 접속 지연을 줄이는 것이 좋다. 이는 Render의 현재 [무료 서비스 안내](https://render.com/docs/free#spinning-down-on-idle)에 근거한다.

이 점검은 실제 사용자의 대회·경기·스킨·계정 데이터를 변경하지 않았다. PostgreSQL 서버와 브라우저 시나리오는 모두 별도 임시 환경을 사용했다. 경기장 네트워크, 운영 배포 버전, 실제 Safari·카카오톡·설치 PWA의 키보드 및 OS 동작은 이번 모의 브라우저 검사만으로 보증하지 않는다.

**행사 전 마지막 확인은 운영 앱에서 관리자·선수 각 1개 계정의 로그인과 대회 조회, 참가자 명단 확인이다. 기록 입력은 위에서 검증한 대회 화면으로 통일하면 된다.**
