## 1 종합 판단과 검토 범위

**판정은 조건부 운영 적합이다.** 경기 기록 서비스의 기본 구조, 권한 분리, 데이터 제약, 자동 검증은 잘 마련되어 있다. 대규모 재작성보다 초기 관리자 보안과 비동기 저장 신뢰성을 우선 수정하는 것이 효과적이다. 모바일에서는 화면이 정상적으로 보이는 것과 기록이 안전하게 저장되는 것을 별도로 평가해야 한다.

**현재 자료만으로 iOS와 Android에서 문제가 없다고 보증할 수 없다.** 최신 브라우저를 위한 설치·safe area·화면 높이 대응은 존재한다. 그러나 가상 키보드, OS 뒤로가기, 앱 종료, 저장 중 네트워크 전환, VoiceOver와 TalkBack, 구버전에서의 동작은 실제 기기 검증이 필요하다. Chromium의 모바일 크기 검사 통과를 iPhone 호환성 통과로 환산하지 않았다.

**우선 의사결정 세 가지**

- 운영 초기 관리자 비밀번호의 공개된 기본값을 제거한다. 이미 운영 중인 계정의 실제 비밀번호는 이번 검토에서 조회하지 않았다.
- 기록 저장 완료와 화면상 성공을 구분한다. 게임 점수 큐, 오래된 인증 응답, 응답 본문 제한 문제를 공통 요청 수명 관리와 회귀 테스트로 해결한다.
- 지원 OS·브라우저 범위와 온라인 전용 정책을 명시한다. PWA 설치 성공만으로 오프라인 사용·장기 로그인·백그라운드 저장을 보장하지 않는다.

## 3 보안과 운영 통제

**SEC01 최초 관리자 자격 증명**

**SEC03 전달 IP와 로그인 횟수 제한**

Uvicorn은 별표가 전체 신뢰를 의미한다고 설명하며, Render도 앞단 프록시가 추가한 주소와 호출자 제공 주소를 구분하도록 안내한다. [Uvicorn 설정](https://uvicorn.dev/settings/), [Render 전달 헤더 주의사항](https://render.com/articles/host-pocketbase-on-render)

운영 경로에서 신뢰할 프록시와 실제 접속 주소 추출 규칙을 먼저 정한다. 임의의 첫 번째 IP를 신뢰하거나 임의의 마지막 IP를 사용자 주소로 바꾸는 단순 수정은 피한다. 완료 기준은 위조 단일·복수 전달 헤더로 같은 사용자의 제한 버킷을 바꾸지 못하고, 서로 다른 정상 사용자는 구분되는 것이다.

**OPS01 관리자 장기 세션**

**이미 있는 방어와 보강 범위**

[OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

## 4 데이터와 비동기 요청의 신뢰성

**REL01 PostgreSQL 초기화 교착**

[admin.py:370](C:/Users/jaehe/scutta/backend/app/api/admin.py:370)은 대회 테이블들을 먼저 독점 잠근 뒤 사용자 테이블을 잠근다. 일반 요청은 인증 조회에서 사용자 테이블의 읽기 잠금을 유지한 채 대회 조회로 진입한다. 격리 PostgreSQL 17에서 실제 인증·초기화 코드로 이 순환 대기를 재현했고 DeadlockDetected로 초기화가 실패했다. 임시 서버는 종료했으며 기존 DB는 사용하지 않았다. 인증까지 포함한 트랜잭션 경계와 잠금 순서를 통일하고, 조회·결과 제출·비밀번호 변경·동시 초기화가 함께 실행되는 회귀 검사를 추가한다.

**DATA01 SQLite의 연결되지 않은 경기**

[competitions.py:1251](C:/Users/jaehe/scutta/backend/app/services/competitions.py:1251)의 대진 조회와 신규 경기 연결은 PostgreSQL 행 잠금에 의존한다. 파일 기반 SQLite에서 빈 대진을 두 요청이 읽고 서로 다른 날짜의 결과를 쓰도록 했을 때, 경기 2개와 대진 링크 1개가 남았다. 연결되지 않은 경기도 전체 통계에 집계된다. 로컬 SQLite의 조건부 결함으로 한정하며, 운영 PostgreSQL에서 같은 현상을 확인했다는 의미가 아니다. SQLite 쓰기를 직렬화하거나 조건부 연결 갱신 실패 시 경기 생성까지 롤백해야 한다.

## 6 백엔드 성능과 확장 기준

## 9 PWA 오프라인 갱신과 앱 생명주기

**온라인 전용 범위를 명시한다.** 현재 SW는 화면 자산을 사전 저장하며 API 응답 캐시나 오프라인 경기 제출 큐는 없다. API·health 경로는 SPA fallback에서 제외한다. 새 실행 시 인증 조회가 필요하므로 오프라인으로 실행하면 연결 오류 화면에 도달할 수 있다. 친목 기록 서비스가 온라인 전용인 것은 합리적인 선택이며 그 자체가 PWA 결함은 아니다. 앱 설치 안내가 오프라인 기록 보존을 암시하지 않도록 해야 한다.

오프라인 쓰기를 도입할 때에는 단순 fetch 재시도보다 사용자별 대기함, 중복 방지, 서버 처리 결과 확인, 로그아웃 시 격리, 초기화 세대 처리, 오래된 자료 표시가 필요하다. 개인 API 전체를 CacheFirst로 바꾸면 계정 전환·데이터 최신성 문제가 생길 수 있다. 먼저 현재 게임의 저장 큐 손실과 연결 복구를 해결한다.

**PWA01 업데이트 재접근과 활성화 확인**

[PwaManager.tsx:186](C:/Users/jaehe/scutta/frontend/src/components/PwaManager.tsx:186)에서 알림을 닫으면 같은 세션에 다시 여는 설정 메뉴가 없다. 동일한 waiting worker가 계속 있을 때 갱신 확인이 알림을 다시 띄운다는 보장도 없다. 설정에 현재 버전과 업데이트 준비 상태를 남기고 사용자가 다시 적용할 수 있게 한다.

[pwaUpdate.ts:57](C:/Users/jaehe/scutta/frontend/src/components/pwaUpdate.ts:57)은 3초 후 활성화 확인 없이 새로고침하는 fallback이 있다. 무한 대기를 피하려는 의도는 이해되지만 느린 activation이나 다중 탭에서 새 버전 적용 여부가 모호해질 수 있다. 새 controller 또는 activated 상태 확인 후 새로고침하고, 제한 시간 초과는 재시도 가능한 상태로 처리하는 방향을 검토한다. SW의 install·waiting·activate 단계는 구분해야 한다. [PWA 업데이트 생명주기](https://web.dev/learn/pwa/update)

운영 배포는 새 UI와 이전 API, 이전 UI와 새 API가 잠시 공존한다고 가정한다. 현재 사용자 선택 갱신은 입력을 보호하는 장점이 있지만 구형 클라이언트가 남을 수 있다. API 계약을 한 버전 이상 호환하고, 즉시 제거가 필요한 변경은 별도 안내와 복구 경로를 준비한다. 같은 origin에서 /api와 정적 화면을 함께 서비스하는 구조는 유지해도 된다.

**백그라운드 전환과 종료**

Canvas는 전면 복귀 때 프레임 시간차를 초기화한다. 그러나 복귀 직후 자동 재개보다 탭해서 계속하는 방식이 손실과 당황을 줄일지 실기기로 확인할 필요가 있다. OS가 앱을 종료하면 React state와 메모리 큐가 사라진다. hidden 이벤트 이후 추가 JavaScript 실행이나 unload 이벤트를 보장할 수 없으므로 종료 직전에만 저장하는 설계는 충분하지 않다. [Chrome 페이지 생명주기](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

**완료 판정 시나리오**

- 새 버전 배포 후 입력 중 강제 새로고침이 없고, 저장 뒤 사용자가 갱신을 적용할 수 있다.
- 알림을 닫고 다시 찾을 수 있으며, 설치 앱과 브라우저 탭을 함께 열어도 버전 전환이 복구 가능하다.
- 앱 종료 전 저장 중·완료·실패 상태가 구분되고, 재실행 후 미확정 결과를 중복 없이 확인할 수 있다.
- 비행기 모드, Wi-Fi에서 이동통신 전환, 서버 기동, 저장 응답만 유실되는 경우를 각각 검사한다.

## 11 운영 관측과 출시 검증

Uvicorn의 기본 접근·오류 로그는 존재한다. 그러나 관리자 변경의 행위자·대상·전후 상태·요청 ID를 남기는 감사 이벤트와 애플리케이션 수준의 오류·지연 집계는 부족하다. 초기화, 선수 삭제, 비밀번호 초기화, 경기 정정은 기록 분쟁과 복구에 필요한 최소 이력을 남긴다. 원문 비밀번호와 세션 토큰은 로그에 남기지 않는다. [OWASP 로그 지침](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

## 12 실행 순서와 완료 조건

**첫 단계는 신뢰성과 보안이다.** 초기 관리자 기본값 제거, 인증 세대 처리, 본문 timeout, 게임 저장 큐 손실, PostgreSQL 초기화 교착을 수정한다. 각 수정과 함께 기존 코드에서 실패하고 수정 후 통과하는 좁은 회귀 검사를 추가한다. 점수 순위의 신뢰 수준과 관리자 세션 정책도 운영자가 결정한다.

**두 번째 단계는 모바일 출시 검증이다.** 지원 브라우저 범위를 문서화하고 실제 기기에서 키보드·Back·화면읽기·저장 중 이동·앱 종료·PWA 갱신을 검사한다. 연결 지연·저장 중·실패·완료를 사용자가 구별하도록 한다. 무료 서버를 유지할지 결정하고 cold start에 맞는 읽기 복구 흐름을 검증한다.

**세 번째 단계는 측정에 따른 비용 절감이다.** 마스코트 자산 축소와 미리 읽기 정책 비교를 먼저 수행한다. 운영 지연·풀 대기·느린 SQL을 측정한 뒤 개인 통계 조건 전달, 경기 목록 인덱스, 대회 규모 제한을 적용한다. 측정 목표를 충족하면 캐시·비동기 재작성·별도 통계 저장소는 도입하지 않아도 된다.

| 작업 묶음 | 담당 역할 | 완료를 보여 주는 결과 |
| --- | --- | --- |
| 초기 관리자와 프록시 정책 | 백엔드 운영 | 새 배포·위조 헤더 시험 결과 |
| 요청과 인증 수명 관리 | 프론트엔드 | 부분 본문·이전 401 회귀 검사 |
| 저장 상태와 점수 큐 | 프론트엔드 백엔드 | 이동·종료·계정 변경 시 결과 일관성 |
| 초기화 잠금 | 백엔드 | 운영 DB와 같은 PostgreSQL 동시 시험 |
| 모바일 입력 접근성 | 프론트엔드 QA | OS별 실기기 사례와 합격 기록 |
| PWA 업데이트 복구 | 프론트엔드 QA | 미룸 재접근 다중 탭 갱신 시험 |
| 전송과 조회 비용 | 프론트엔드 백엔드 | 자산 크기 및 동일 조건 전후 측정 |
| 복구와 감사 기록 | 운영 백엔드 | 실제 복원 훈련과 사건 추적 사례 |

담당 역할은 제안이며 실제 팀 배정이나 일정 약속이 아니다. 기능 변경 범위와 운영 규모가 확정되지 않아 임의의 날짜·공수를 정밀 추정하지 않았다.

**출시 판정 기준**

P1이 해결되고, 데이터 손실·인증 상태 오류·운영 DB 교착에 대한 회귀 검사가 통과하며, 선언한 최소 OS의 실제 기기에서 핵심 기록 흐름이 통과해야 한다. 미해결 P2는 운영자가 발생 조건과 대응을 이해하고 수용 여부를 기록한다. PWA 설치·빌드 성공이나 정적 화면 검사만으로 출시 승인하지 않는다.

**재검토할 때 보존할 자료**

커밋, lockfile, 빌드 자산 크기, 자동 검사 로그, 재현 절차, OS별 시험표, PostgreSQL 쿼리 계획과 부하 조건, 복구 훈련 결과를 같은 릴리스 단위로 보존한다. 개인 계정·비밀번호·원문 세션·실제 사용자 이름을 시험 보고서에 포함하지 않는다. 이번 브라우저 검사는 가상 선수 자료를 사용했다.

## 부록 검증 기록과 참고 자료

검사 명령은 저장소의 기존 환경을 사용했다. 백엔드는 ruff check, ruff format --check, pytest 100개 통과, 프론트엔드는 pnpm lint, pnpm test 76개 통과, pnpm build, pnpm verify:build 통과다. 마이그레이션 왕복 검사는 pytest에 포함된다. 별도 Docker 이미지 재빌드와 실제 운영 DB의 alembic 검사를 이번에 수행했다고 주장하지 않는다.

추가 검증은 격리 PostgreSQL 17의 초기화 교착, 파일 SQLite 독립 연결의 대진 경쟁, 메모리 DB의 임의 게임 점수와 장기 세션, Uvicorn 전달 헤더 미들웨어, 실제 프론트 코드에서 추출한 비동기 상태·좌표 재현, 빌드 파일 분석, Chromium 23개 화면 조합이다. 함수 재현은 실제 OS 이벤트를 대체하지 않으며, SQLite 계획은 PostgreSQL 계획을 대체하지 않는다.
